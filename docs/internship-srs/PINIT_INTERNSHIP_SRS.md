# PART A — READ THIS FIRST

## A1. How to use this document (for the Antigravity agent)

This document is both a requirements specification and a work plan. Part D splits the whole job into **small numbered tasks** (T-01, T-02, …). Follow these rules exactly:

1. **Do one task at a time, in order.** Do not start task N+1 until task N passes all its checks.
2. **Read every file listed under "Read first" before you change anything.** Most mistakes come from guessing what a file contains.
3. **Change only the files listed in the task.** If you think another file must change, stop and write a note to the owner instead.
4. **Run the "Verify" commands after every task.** If any check fails, fix it before moving on. Never skip, delete or weaken a test to make it pass.
5. **Commit after every task** with the message given in the task, on branch `main-dis3ku`, and push with `git push -u origin main-dis3ku`.
6. **Never invent facts.** Do not add fake companies, fake mentors, fake students, fake reviews, fake numbers, or features that are not built. If data is missing, show an honest empty state.
7. **Never flip `INTERNSHIP_AVAILABLE` (or the per-tier switches) to `true`** except in the launch task that says so.
8. If a task is marked **BLOCKED (needs owner decision)**, skip it and continue with the next unblocked task. Section C9 lists the decisions.
9. If you are unsure, **stop and ask the owner** rather than guessing. A wrong guess costs more than a question.

## A2. The standard checks (run after every task)

```bash
npx tsc --noEmit          # must print nothing and exit 0
```

A task is **not done** until all three pass. Record the result in your commit message body (for example `tsc ok, npm test 170/170, build ok`).

# PART B — BACKGROUND: EVERYTHING DISCUSSED SO FAR

## B1. The product in one paragraph

PinIT Career OS is a learning platform. Students buy a **certification plan** (1, 3, 6, 9, 12 or 24 months) on one of two tracks, **web_fullstack** or **python_ai**. Each month of a plan is one **course**. Each course has **30 days**; each day has a **long lesson (20–30 minutes)**, **two practice tasks** that are really checked, and a **test after every 5 lessons**. After the courses, the student builds a **capstone project** in 4 sprints and passes an **oral defense**, then gets a **verifiable certificate** with a QR code. The internship is the phase after the capstone. It has **not been built yet** and is hidden from students.

## B6. Why other internship platforms fall short (the real-world problem)

| Platform type | Examples | Problem |
|---|---|---|
| Job boards | Internshala, LinkedIn, Indeed | Only listings. Most students are never selected; no training, no feedback |
| Paid "certificate internships" | Many small sites | No real work, no checking. Employers do not trust the certificates |
| Virtual job simulations | Forage and similar | Good practice, but every student gets the **same** tasks, so answers are copied; little feedback |
| College-arranged internships | Campus programs | Quality varies; often clerical work; weak evidence |

**How PinIT will be better:**

1. **Unique work per student**: every task is generated by AI for that student, so copying does not work.
2. **Everything is checked**: automatic hidden tests, then AI code review, then (from 3 months up) a human mentor.
3. **Honest names**: a simulation is called a simulation; only real outside work is called an industry internship.
4. **Verifiable proof**: every certificate has a QR code and a public page listing exactly what was done.
5. **Built on what the student learned**: tasks use only the skills of the courses in the student's plan.

## C3. Who can start which internship

- **FR-ELIG-1**: A student may start the internship of **their own plan's tier only** (1m → `t1_job_sim`, 3m → `t2_virtual_team`, 6m → `t3_project`, 9m → `t4_industry`, 12m → `t5_fellowship`).
- **FR-ELIG-2**: The internship opens only when the student's **capstone is complete** (`isCapstoneComplete(enrollment)` in `crashCourseProgress.ts` returns true). The server checks this; the browser's view does not count.
- **FR-ELIG-3**: Only the `python_ai` track is eligible in this version.
- **FR-ELIG-4**: A tier whose switch is off (C8) cannot be started, even by calling the API directly.
- **FR-ELIG-5**: One active internship per student per crash enrollment.

## C4. Tier 1 — Python Job Simulation (1 month), detailed

- **FR-T1-1**: On start, the server creates an internship enrollment with a **14-day deadline** (one extension of 7 days allowed, requested by the student, recorded by the server).
- **FR-T1-2**: The server generates a **pretend company profile** with AI (name, business, short README) that is unique per student. It must say clearly that it is fictional.
- **FR-T1-3**: The server generates **5 tickets** with AI, one of each type: (1) bug fix, (2) new function, (3) data cleaning, (4) refactor with no behaviour change, (5) small feature combining earlier work. Tickets use **only Month 1 Python skills** (functions, strings, lists, dicts, loops, errors, classes, simple modules, no files, no network).
- **FR-T1-4**: Tickets unlock **in order**. Ticket N+1 opens only after ticket N passes.
- **FR-T1-5**: Each ticket has a brief, starter code, **visible tests** (shown to the student) and **hidden tests** (never shown). A ticket **passes** only when the server runs the student's code against visible **and** hidden tests and all pass.
- **FR-T1-6**: After a pass, the server asks the AI for a **code review** (scores 1–5 for correctness, readability, edge cases and naming, plus 2 strengths and 2 improvements). The review is advice only; it never changes pass/fail.
- **FR-T1-7**: After all 5 tickets, the student writes a **final stand-up report** (100–300 words: what they built, one problem they solved, what they would improve). The server checks the length and asks the AI whether it matches the tickets (yes/no + reason). If no, the student can edit and resubmit.
- **FR-T1-8**: The server then issues the **internship certificate** (C7) and sets `certificatesIssued.internshipCertHash` on the crash enrollment.
- **FR-T1-9**: If the deadline passes (plus any extension), the status becomes `expired`. The student may restart **once** with newly generated tickets.

## C5. Tier 2 — Virtual Internship – Backend (3 months), detailed

- **FR-T2-1**: On start, the student joins a **matching queue**. The server groups students who started within the same **7-day window** into teams of **3–4**. If no team forms in 7 days, the student continues in **solo mode** with the same backlog scaled to one person.
- **FR-T2-2**: The server generates with AI a **product brief** for a small Python + SQL backend (for example a library, clinic booking or canteen system), with a data model, 12–16 user stories, and an assignment of stories to members. The skills used must come from Months 1–3 (Python, data structures and algorithms, SQL/PostgreSQL).
- **FR-T2-3**: The internship lasts **4 weekly sprints**. Each sprint has a goal and a due date.
- **FR-T2-4**: Every week, each member gets **2 AI-generated checked tasks** tied to their stories (one Python, one SQL). Python tasks are checked with the server Python sandbox; SQL tasks with PGlite (`runSqlPractice`). Same hidden-test rules as Tier 1.
- **FR-T2-5**: Each team has one **public GitHub repository** (link submitted by a team member, probed with `probePublicUrl`). Each member submits at least **one pull request link per sprint** (`https://github.com/<owner>/<repo>/pull/<n>` in the team repo). The server checks that the link exists and belongs to the team repo.
- **FR-T2-6**: Each member writes a **weekly async stand-up** (done / next / blockers, 30–200 words).
- **FR-T2-7**: At the end of each sprint, a **mentor review** (D1) approves or requests changes. **Until mentors exist**, the AI reviews the sprint (tasks passed, PR links, stand-ups) and an admin can spot-check. The AI review alone may approve Tier 2 sprints only while the D1 default applies (C9).
- **FR-T2-8**: **Final demo**: the team submits a deployed https URL (probed like capstone Sprint 3) and each member takes a short **AI oral defense** reusing the capstone interview signing (`evaluationSignature.ts`, `capstoneInterview.ts`) with the topic "Virtual Internship – <project name>".
- **FR-T2-9**: A member completes the internship when **all 4 sprints are approved**, **all their weekly tasks passed**, and **their defense passed**. The certificate then lists the project, the team size and the member's stories.

## C6. Tiers 3, 4 and 5 — real-world internships

These tiers depend on real people and organisations, so most of their tasks are **BLOCKED until the owner decides D1 and D2**. The software parts that can be built without those decisions are marked as unblocked in Part D.

Work lasts 6–8 weeks with weekly logs (hours, summary, links) and a weekly mentor review. The final evidence is a public repository and a deployed service (probed).
- **FR-T3-2 (fallback)**: If no real opportunity is available when the student becomes eligible, they may take a **simulated-client project**: the AI plays a client in a chat with changing requirements. It must be named **"Project Internship (simulated client)"** on the certificate.

## C12. AI generation and the validation pipeline (most important section)

AI makes mistakes. While building the Month 10–12 courses, more than **20 expected answers in AI-written tasks were wrong** and had to be fixed by running the code. Therefore **no AI-generated task may reach a student until the server has proved it works**.

**Generation (per task):**

1. Build the prompt from: the tier, the skill list of the student's completed courses, the task kind, the company profile, and a random **seed** (stored in `generation_meta`).
2. Ask the model for **strict JSON** with fields `title`, `brief`, `starter_code`, `visible_tests`, `hidden_tests`, `reference_solution`, `skills` (and `sql_setup` for SQL tasks).
3. Parse the JSON with a `zod` schema. On failure, retry (max 3 attempts per task, D5).

**Validation (all must pass, in this order):**

| Step | Check | Why |
|---|---|---|
| V1 | Every text field is within length limits (brief ≤ 2,000 chars, code ≤ 6,000, tests ≤ 6,000) | Stops runaway output |
| V2 | `findForbiddenPython` (from `pythonGuard.ts`) finds nothing in starter code, tests or solution | The sandbox refuses those patterns |
| V3 | `reference_solution` + `visible_tests` **pass** in the sandbox | The task is solvable |
| V4 | `reference_solution` + `hidden_tests` **pass** in the sandbox | The hidden tests are correct |
| V5 | `starter_code` + `visible_tests` + `hidden_tests` **fail** | The task is not already solved |
| V6 | The brief does not contain the reference solution (no line of the solution longer than 20 characters appears in the brief) | No answer leaks |
| V7 | Hidden tests contain at least 3 `assert` lines, visible tests at least 2 | Enough checking |

If all 3 attempts fail, set the enrollment to `generation_failed` and show: "We could not prepare your internship right now. Please try again in a few minutes." **Never** fall back to hand-written tasks (owner rule B3-4).

**AI review and report checks** use the same helper with a strict JSON schema. If the AI call fails, the student's pass still stands and the review shows "Review not available right now."

**Cost control:** rate-limit generation (1 start per student per 10 minutes), store every generation, never regenerate a task that already passed.

## E1. Glossary

| Word | Meaning |
|---|---|
| Crash enrollment | A student's purchase of a certification plan (`user_crash_enrollments`) |
| Tier | The internship level that belongs to a plan length (C2) |
| Ticket | One Tier-1 task, like a bug report at a real company |
| Visible tests | Checks the student can see and run |
| Hidden tests | Extra checks only the server runs, so students cannot just satisfy the visible ones |
| Reference solution | The AI's own answer, used only to prove the task is solvable |
| Sandbox | The server's safe Python runner (timeouts, blocked dangerous code) |
| Stand-up | A short daily/weekly update: done, next, blockers |
| Sprint | One week of team work with a goal |
| Mentor | A human engineer who reviews student work (D1) |
| Supervisor | The student's manager at a real outside company (Tiers 4–5) |
