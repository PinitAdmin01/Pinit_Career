# PART A — READ THIS FIRST

## A1. How to use this document (for the Antigravity agent)

This document is both a requirements specification and a work plan. Part D splits the job into **small numbered tasks** (W-00-1, W-01, W-02, …). Follow these rules exactly:

1. **Do one task at a time, in order.** Do not start the next task until the current one passes all its checks.
2. **Read every file listed under "Read first" before you change anything.**
3. **Change only the files the task names.** If another file seems to need changing, stop and ask the owner.
4. **Run the standard checks (A2) after every task.** If one fails, fix your change. Never skip, delete, silence or weaken a test (this includes adding an early `return` inside a test).
5. **Commit after every task** with the message given, on branch `main-dis3ku`, then `git push -u origin main-dis3ku`.
6. **Never push to `main`.** The owner (or Claude Code) merges through a pull request after the "Web app tests" check passes.
7. **Never invent facts, data, companies, reviews or results.** Report only what you ran and saw.
8. **Stop at the end of every phase** and report to the owner in the format in A5. Wait for "continue".
9. If a task is marked **BLOCKED**, skip it and continue with the next unblocked task.
10. If something in this document does not match the real code, **stop and ask**. Do not guess.

## A2. The standard checks (after every task)

```bash
npx tsc --noEmit          # must exit 0 with no output
npm test                  # every test must pass; the total must never go down (383 at the time of writing)
npx next build            # must finish without errors
git status --short        # must NOT list tsconfig.tsbuildinfo in your commit (restore it with: git checkout -- tsconfig.tsbuildinfo)
```

## A3. Mistakes the agent must avoid (all of these happened before in this project)

| # | Mistake | What to do instead |
|---|---|---|
| 1 | Declaring the same `const` twice in one scope | Use another name or reuse the variable |
| 2 | Duplicate keys in an inline style object | One key per property |
| 3 | Using `any` | Use or import the real type |
| 4 | Trusting data from the browser (passed, score, progress) | Only the server decides and records results |
| 5 | Sending hidden tests or reference solutions to the browser | Select explicit columns; use the `toClient` mappers |

## C3. Content of the three new courses and Node

Topics are listed by day group; each day gets 2 tasks that exercise that day's idea.

**`course-node-web` — Node.js & TypeScript Backend Engineering (Month 2):**

- Days 1–5: the Node runtime and event loop; modules; TypeScript basics for the backend (types, interfaces, generics, narrowing); async/await and errors.
- Days 6–10: the HTTP protocol (methods, status codes, headers); building request handlers as pure functions; routing tables; query strings and URL parsing; request body validation with Zod-style schemas.
- Days 11–15: middleware chains; error handling with RFC 7807 problem details; structured logging; configuration and environment variables; pagination and filtering.
- Days 16–20: authentication (password hashing concepts, sessions vs tokens, JWT structure and expiry checks); authorization rules; rate limiting; CORS; input sanitising.
- Days 21–25: data access layers; repository pattern over an in-memory store; transactions (concept); caching with TTL; idempotency keys.
- Days 26–30: testing handlers; OpenAPI descriptions; background jobs and retries; graceful shutdown and health checks; capstone: a small REST API.

**`course-sre-web` — Multi-Cloud Reliability & SRE in TypeScript (Month 10):**

- Days 1–5: SLIs, SLOs, error budgets and burn rates; availability math (serial and parallel).
- Days 6–10: infrastructure as code as data (plan/diff/apply of resource maps, drift detection); multi-region and failover planning.
- Days 11–15: load balancing algorithms; health checks; retries with backoff and jitter; circuit breakers; bulkheads and timeouts.
- Days 16–20: observability (metrics, percentiles, histograms, log parsing, trace spans); alert rules and noise reduction.
- Days 21–25: incident response (severity, timelines, MTTD/MTTR); postmortems; capacity planning; cost models.
- Days 26–30: chaos experiments; deployment strategies (blue/green, canary analysis); runbooks as code; capstone: a reliability scorecard.

**`course-stream-web` — High-Throughput Streaming in TypeScript (Month 11):**

- Days 1–5: event logs and offsets; producers/consumers; partitioning by key; ordering guarantees.
- Days 6–10: consumer groups and rebalancing; commit strategies; at-most/at-least/exactly-once; deduplication.
- Days 11–15: backpressure and bounded queues; batching and linger; compression trade-offs; throughput vs latency math.
- Days 16–20: stream processing (map/filter/reduce over streams); tumbling, sliding and session windows; watermarks and late events.
- Days 21–25: joins (stream–table, stream–stream); state stores; checkpoints and recovery; schemas and evolution.
- Days 26–30: dead-letter queues; replay; monitoring lag; capacity planning; capstone: a windowed analytics pipeline.

**`course-aideploy-web` — Production AI Deployment in TypeScript (Month 12):**

- Days 1–5: calling model APIs safely (timeouts, retries, typed responses); token counting and cost estimates; prompt templates.
- Days 6–10: streaming responses (parsing server-sent events); request batching; semantic caching with similarity thresholds; rate limiting per user.
- Days 11–15: model routing and fallbacks; latency budgets and percentiles; quantization and model-size trade-offs (as calculations); GPU/CPU capacity math.
- Days 16–20: retrieval-augmented generation plumbing (chunking, top-k merge, citations); output schema validation; guardrails (input validation, prompt-injection patterns, PII masking).
- Days 21–25: evaluation harnesses and regression gates; A/B comparisons; feedback logging; drift detection.
- Days 26–30: observability for AI calls; cost dashboards; incident handling; deployment checklists; capstone: a guarded, cached, observable AI endpoint.
