## 📜 Architectural Decisions Log
1. **Zero Fake Data:** All examples use real standards, POSIX concepts, and genuine JavaScript/Node.js behaviors.
2. **Zero Answer Leakage:** Starters, hints, and diagnostics guide Socratic discovery without giving away solutions.
3. **Fact Classification Standard:** Every core claim is tagged as Language Spec, Runtime Behavior, Hardware Invariant, or Teaching Model.
4. **Scope Discipline:** Exclude advanced abstractions until their designated months.
5. **Yielding Invariant:** Microtasks drain before the next task and before rendering; task yielding (e.g. `scheduler.yield` with task fallback) is mandatory for unblocking main-thread input responsiveness.
6. **Native-First Accessibility:** Evaluate platform HTML controls before building custom ARIA widgets.
7. **RFC 9457 Error Standard:** Fullstack error architecture standardizes on RFC 9457 (which obsoletes RFC 7807), maintaining distinct separation between core standard properties and application-specific error extensions.
8. **Asynchronous I/O Invariant:** JS callbacks execute on the single event-loop thread. Adding `async` to a synchronous CPU loop does not make it concurrent or non-blocking; OS non-blocking primitives and libuv worker pools handle distinct asynchronous operations.
9. **Real-Runtime Truth Invariant:** Passing simulations or mock environments is never sufficient for systems/database gates. Conceptual models may use simulations for mental understanding, but authoritative gate verification must execute against the real system/runtime (e.g. Native PostgreSQL multi-session over TCP with isolated test schemas).
10. **The Untrusted Client Boundary Invariant:** The browser is an untrusted client environment. TypeScript types are erased at compile-time and provide zero runtime network safety. Client-side route guards are UX navigation aids only. The API is the sole authorization boundary, and PostgreSQL is the persistence and relational integrity boundary.
11. **The Architectural Boundary & Persistence Transparency Invariant:** Modules enforce in-process boundaries; domains protect business invariants independently of transport; application services own the transaction boundary; and ORMs automate object-relational mapping without obscuring SQL execution, query counts, or database migrations.
12. **The In-Memory Performance, Eviction & Concurrency Boundary Invariant:** Redis provides sub-millisecond in-memory caching and coarse distributed coordination, but is not an ACID relational database or a Paxos/Raft consensus engine. Memory is bounded and subject to probabilistic or configured eviction; TTLs are non-instantaneous; distributed lock leases do not guarantee mutual exclusion under latency overrun; multi-step rate-limiting and lock release require atomic server-side Lua scripts or Redis Functions; and production cache architectures must expose complete telemetry (hit/miss, fallbacks, lock contentions, P99 latency) to safeguard the database layer.
13. **The Distributed Asynchronous Processing, Idempotency & Outbox Invariant:** For BullMQ-based task processing, at-least-once delivery is the physical baseline; workers must be idempotent, retry-safe, and duplicate-tolerant. Stalled is an event/condition resulting from un-renewed lock leases, not a persistent job state. Concurrent processing alters completion order; ordering scopes must be explicitly defined. Deterministic errors must short-circuit retries using native `UnrecoverableError`. Exponential backoff must incorporate full jitter to eliminate downstream thundering herds. Idempotent business processing requires an atomic claim/lease/result lifecycle (`PENDING` -> `PROCESSING + lease` -> `COMPLETED`) with fencing tokens to prevent expired stale workers from overwriting newer owner state. External API integrations must use provider-side idempotency keys or explicit reconciliation strategies. DLQ movement must be idempotent with temporary coexistence accepted as a valid recovery state. The Transactional Outbox pattern guarantees atomic persistence of state and event intent within a single PostgreSQL ACID transaction, but publisher crashes emit duplicate downstream events requiring idempotent consumers. Kafka guarantees ordering strictly within a partition, with consumer groups distributing partitions for horizontal scalability.
14. **The Persistent Real-Time Channel, Backpressure & Bounded Presence Invariant:** Real-time communication over WebSockets (RFC 6455) transforms client-initiated request-response interactions into stateful, persistent bidirectional channels. In Node.js, this is achieved via the `upgrade` event handler transferring the underlying TCP socket to the WebSocket frame engine. Client-to-server frames must always be masked to prevent intermediary proxy cache poisoning and request smuggling; unmasked client frames must trigger immediate connection termination. Transport-level reachability and application-level health are distinct signals; applications that require timely detection of dead peers must implement an application-level liveness policy appropriate to their requirements. Unresponsive zombie sockets must be destroyed using `terminate()` to release socket tracking without waiting for close handshakes across broken connections. Client reconnection must enforce exponential backoff with full jitter to eliminate server reconnection thundering herds. Applications must use `bufferedAmount` as a congestion and backpressure signal to prevent slow consumers from exhausting server heap memory. Multi-server scaling requires an out-of-process broadcast bus (Redis Pub/Sub) with dedicated subscriber connections; Pub/Sub provides at-most-once delivery, requiring Redis Streams or durable message queues when replay is required. Ephemeral presence is intentionally eventually consistent and bounded by the lease/TTL policy, using Redis key TTLs to ensure that ungraceful disconnects naturally purge online status within the defined bounded staleness window.
15. **The Defense-in-Depth, Zero-Trust Boundary & Cryptographic Identity Invariant:** Perimeter security is obsolete; modern systems assume breach and enforce default-deny at every trust boundary crossing. Threat modeling (STRIDE) precedes implementation. As mandated by OWASP Top 10:2025, Broken Access Control is the primary attack vector, requiring atomic ownership scoping in database queries rather than relying on network WAFs or client-side guards. Public clients cannot protect secrets; enterprise identity and delegation must use OAuth 2.0 / OpenID Connect adhering to RFC 9700 Security Best Current Practice. Public clients must use the Authorization Code Flow fortified by Proof Key for Code Exchange (PKCE, RFC 7636) with SHA-256 (`S256`). Clients must validate `state` to prevent Login CSRF and OIDC `nonce` to prevent ID token replay. JSON Web Tokens must be verified against signature, issuer (`iss`), audience (`aud`), and expiration (`exp`); asymmetric signing (RS256/ES256) enables verification across distributed services without disseminating signing private keys. Refresh tokens must enforce one-time rotation (RTR), and any reuse of an invalidated refresh token must trigger immediate revocation of the entire token family to defend against credential replay theft.
16. **The Database-Enforced Row-Level Security, Role Privilege Isolation & Trusted Tenant Authority Invariant:** Application-level `WHERE tenant_id = $1` filters violate defense-in-depth and cause Confused Deputy vulnerabilities when queries, joins, or background tasks omit tenant scoping. Multi-tenant data isolation must be enforced at the database engine level using PostgreSQL Row-Level Security (`ENABLE/FORCE ROW LEVEL SECURITY`). Neither `ENABLE` nor `FORCE` protects against superusers or roles granted the `BYPASSRLS` attribute; production runtime queries must execute as a dedicated least-privileged role (`NOSUPERUSER NOBYPASSRLS`). Tenant context must be injected strictly inside a transaction block using `SET LOCAL app.current_tenant_id = '...'` so that connection poolers (`pg.Pool`, PgBouncer) discard the tenant setting upon `COMMIT` or `ROLLBACK`, preventing cross-request socket contamination. Critically, tenant authority must strictly originate from verified identity tokens or authenticated session claims—never from untrusted request bodies (`req.body.tenantId`).
17. **The Two-Tier AAD Envelope Encryption, Memory Hygiene & W3C CSP Level 3 Nonce-Based Script Authorization Invariant:** High-entropy cryptographic material must never be committed to source control or persisted in plaintext `.env` files. Multi-tenant field-level encryption requires a two-tier Envelope Encryption hierarchy: a master Key Encryption Key (KEK) maintained inside a KMS/HSM architectural boundary (modeled via KMS key-wrapping architecture in laboratory implementation) wraps ephemeral Data Encryption Keys (DEKs) generated per record. Ciphers standardize on AES-256-GCM with 96-bit (12-byte) IVs per NIST SP 800-38D, strictly enforcing per-key IV uniqueness to prevent algebraic recovery of the GHASH authentication subkey H. Ciphertext must be bound to its operational security context (tenant ID, record ID, field name, version) using Additional Authenticated Data (AAD) to neutralize ciphertext transplant and replay attacks across records or tenants. Overwriting the `plaintextDEK` Buffer with zeros immediately after use (`Buffer.fill(0)`) is enforced as best-effort memory hygiene to minimize process memory exposure. Master key rotation re-wraps DEKs under `KEK_v2` without decrypting or re-encrypting underlying database rows. At the browser boundary, CORS does not protect against CSRF on simple requests; anti-CSRF requires session-bound HMAC Double Submit Cookies with length-safe constant-time comparison (`timingSafeEqual`). Modern script authorization mandates W3C Content Security Policy Level 3 using cryptographically random 128-bit per-response nonces, `'strict-dynamic'`, `base-uri 'none'`, and `frame-ancestors 'none'`, omitting `'unsafe-inline'` fallbacks; this provides strong CSP3 enforcement in supporting user agents; legacy or non-conforming clients require separate compatibility/security consideration.
18. **The Ephemeral Database Isolation & Real-Engine Fidelity Invariant:** Unit tests verify pure domain algorithms in memory without I/O. Integration tests that touch persistence must execute against the real target database engine (PostgreSQL 18.x), never against mock in-memory substitutes (SQLite, H2, mock-knex) which conceal dialect incompatibilities, constraint behaviors, JSONB semantics, and concurrency locks. To prevent test interference and socket port exhaustion (`EADDRINUSE`) in parallel execution, integration test harnesses must either use dynamically assigned container ports (Testcontainers) or isolate each test worker within an ephemeral, dedicated database schema (`SET search_path = 'test_<uuid>'`) dropped upon test completion. Teams must distinguish session-scoped `SET search_path` from transaction-scoped `SET LOCAL search_path`. Containers should utilize automated reaper processes (such as Ryuk) to assist with resource cleanup after unexpected runner crashes, while maintaining mandatory explicit teardown in test lifecycles.
19. **The Consumer-Driven Contract Verification, Auto-Waiting & Governed Flaky Quarantine Invariant:** Microservice and full-stack API boundaries must eliminate schema and behavioral drift through Consumer-Driven Contract Testing (Pact). Consumers author contract specifications using flexible type matchers (`Match.like()`, `Match.eachLike()`, `Match.regex()`) rather than brittle literal constants. Providers must verify contracts against real HTTP endpoints using explicit Provider State handlers before deployment. In browser automation, arbitrary sleep statements (`waitForTimeout`) are strictly prohibited; Playwright tests must synchronize using native actionability checks and web-first assertions with polling backoff. Non-deterministic tests must not be masked with blind retry loops; flaky tests must be governed through a strict quarantine lifecycle (Owner $\to$ Reason $\to$ Issue $\to$ SLA $\to$ Review) while maintaining a zero-tolerance 100% green bar for merge-blocking CI gates. Code coverage alone does not prove test quality; critical business logic must demonstrate sensitivity through mutation testing.
20. **The POSIX Process Hierarchy, Kernel Signal Sandboxing & Container Virtualization Invariant:** Production services execute on operating system process trees rooted at Init/PID 1. Systemd supervision standardizes on `Type=exec` for standard binary execution; services declaring `Type=notify` must explicitly implement the `sd_notify(3)` socket protocol sending `READY=1` over `$NOTIFY_SOCKET` to avoid startup timeout termination. Graceful shutdown requires trapping catchable signals (`SIGTERM`, `SIGINT`) to drain in-flight connections before uncatchable `SIGKILL` termination. Linux containers are isolated host processes governed by Linux Namespaces (PID, NET, MNT, IPC, UTS, USER) and Cgroups v2 unified controllers (`cpu.max`, `memory.max`, `memory.high`, `io.max`), sharing the host Linux kernel (or the virtualized Linux kernel provided by Docker Desktop on Windows/macOS). Production container images must enforce multi-stage build separation, layer caching optimization, and least-privileged unprivileged execution (`USER node`), strictly omitting compilers, devDependencies, and build caches from the shipping image.
21. **The Multi-Service Bridge Isolation, Service Discovery & Compose Healthcheck Invariant:** Multi-container applications orchestrated via Docker Compose v2 (`compose.yaml`) automatically share the project's default bridge network unless customized. Explicit custom bridge networks establish intentional security boundaries between application tiers (frontend edge vs isolated database backend). Service discovery is resolved via the embedded Docker DNS engine (`127.0.0.11`), mapping service names to dynamic container IPs. Port publishing (`ports: ['host:container']`) binds container ports to host network interfaces, whereas port exposure (`expose: ['container']`) documents or restricts reachability exclusively to sibling containers on shared bridge networks. Named volumes provide Docker-managed storage with host/runtime-dependent performance and filesystem semantics. Service dependencies must never rely on naive `depends_on` array syntax; orchestrating database dependencies mandates `depends_on: { db: { condition: service_healthy } }` coupled with active healthchecks (`pg_isready -U postgres`) to eliminate process-running versus engine-ready startup crash races.
22. **The Immutable Git DAG, Fast-Forward Merge & Logarithmic Bisect Invariant:** Git's internal data model is a content-addressable Directed Acyclic Graph (DAG) of cryptographically hashed objects (`<type> <size>\0<content>`): Blobs (pure file payload), Trees (directory listings), Commits (immutable snapshot plaques pointing to a root Tree and parent commit hashes), and Annotated Tag Objects. Annotated tag objects are Git objects that can reference another Git object; tag refs provide mutable names for those objects. Fast-forward merges (`--ff-only`) advance branch pointers linearly without creating merge commits when no divergence exists; 3-way merges (`--no-ff`) preserve divergent branch topology via explicit two-parent merge commits. Interactive rebasing (`git rebase -i`) replays commits on a new base, generating brand-new commit hashes due to altered parent pointers; rebasing shared public branches is strictly prohibited because rewriting hashes forces collaborator history divergence. Regressions across candidate histories are isolated using `git bisect`, which operates under an O(log n) conceptual search bound under suitable good/bad assumptions (testing <= 10 steps for 1,000 candidate commits); automated validation uses `git bisect run <test_script>` exiting code 0 (good) versus non-zero (bad).
23. **The Cloud Network Boundary, Least-Privilege IAM & Pre-Signed Storage Invariant:** Production cloud infrastructure adheres to the AWS Well-Architected Framework across its 6 Pillars (Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, Sustainability). Global topology isolates physical blast radiuses across Regions, Availability Zones (independent power/cooling within <2ms transit), and Edge Locations. Security governance mandates root account lockdown (protecting the root user with MFA, preferring phishing-resistant passkeys/security keys where supported, and strictly prohibiting root API access keys). Identity and Access Management (IAM) enforces least privilege with temporary STS `AssumeRole` credentials; explicit Deny overrides all allows. The Shared Responsibility Model is service-dependent: EC2 requires customer guest OS patching and firewall management, whereas AWS Fargate and managed RDS offload infrastructure and operating system maintenance to AWS while the customer retains configuration, data, IAM, and application control. Network architecture partitions VPCs into 3 tiers: public subnets (routed to an Internet Gateway; note that public subnet placement does not automatically assign public IPv4 addresses), private application subnets (routed to multi-AZ NAT Gateways), and isolated database subnets (zero internet ingress/egress). Stateful Security Groups automatically track and allow return traffic regardless of outbound rules, whereas stateless Network ACLs evaluate subnet rules in strict numerical order and require the appropriate client/source ephemeral return-port range; 1024-65535 is a broad compatibility example, not a universal range. Ingress traffic is balanced at Layer 7 by Application Load Balancers (ALB) performing host/path routing and ACM TLS termination, with configured HTTP 301 or 302 redirect actions enforcing HTTPS at the load balancer listener. Web servers are orchestrated via versioned ECS Task Definitions and managed Services using serverless Fargate MicroVM compute. Cloud object storage standardizes on Amazon S3 with Block Public Access (BPA); large binary transfers should avoid proxying or intentionally buffering the file payload through application-server memory; clients should upload directly to object storage using appropriately scoped, time-bounded pre-signed URLs. Managed database tiers use Amazon RDS Multi-AZ DB instances for synchronous replication with an RPO = 0 objective and automated failover, while read scaling uses asynchronous Read Replicas subject to replication lag and non-zero RPO data loss hazards.
24. **The CloudWatch Observability, Metric Mathematics & Composite Alarm Invariant:** Standard CloudWatch metrics use one-minute granularity. High-resolution custom metrics can be published at one-second resolution. Alarm/retrieval periods may aggregate these observations differently. Metric filters extract numeric dimensions from structured JSON logs sequentially from their creation timestamp forward; metric filters do not retroactively backfill metric historical data points for past logs. The `SEARCH()` metric math function is designed for dynamically querying and visualizing metrics in dashboards; it cannot be used directly as a metric-alarm expression because alarms require an expression that resolves to a supported single time series (or supported Metrics Insights queries). In alert architecture, M-of-N datapoint evaluation belongs to underlying metric/log alarms. Composite alarms combine the resulting alarm states using Boolean operators (`AND`, `OR`, `NOT`) or functions such as `AT_LEAST`. Alarm suppressors prevent composite alarm actions from firing without altering the underlying independently evaluated alarm state (composite alarm enters ALARM with actionsSuppressed true). Distributed tracing requires unambiguous trace context propagation (`traceparent` header per W3C Trace Context recommendation) across every service boundary to correlate downstream failures back to root ingress requests.
25. **The Distributed Consensus, CAP/PACELC Trade-Off & Qualified Consistent Hashing Invariant:** When a network partition occurs, a distributed system cannot simultaneously provide the specified consistency and availability guarantees. CAP and PACELC are analytical frameworks for evaluating particular configurations, topologies, and workloads—not permanent, immutable product badges. In normal (non-partitioned) operation, systems are governed by the PACELC theorem, making an explicit trade-off between Latency (L) and Consistency (C). Read/write splitting introduces replication lag; architectures requiring read-your-own-writes guarantees must route recent-writer sessions to the primary writer for a configurable, workload-derived primary-pinning window based on observed replica lag and consistency requirements. When consistent hashing is selected for distributed key placement, virtual nodes (vnodes) can improve distribution and reduce movement during membership changes. 128 virtual nodes is an illustrative lab parameter; production vnode counts must be selected based on distribution variance and memory/routing overhead. Under an idealized evenly distributed consistent-hashing model, adding one node moves approximately K / (N + 1) keys, with actual distribution depending on the hash function, vnode placement, and workload. For a simple replicated-storage quorum model, R + W > N guarantees that read and write quorums overlap. Quorum intersection is a necessary property for many quorum-consistency designs, but does not by itself define a complete consistency protocol. Strong consistency requires additional assumptions about replication protocols, version ordering, failure handling, and read/write semantics. Weak quorums (R + W <= N) permit stale reads or conflicting versions.
26. **The Quantitative Capacity Planning, Fault-Isolation Bulkhead & Chaos Resilience Invariant:** Architecture specifications must be quantitatively grounded from explicitly declared workload assumptions: peak traffic must be modeled from measured traffic distributions or explicitly stated burst factors; storage trajectories must be modeled from actual components (row/payload size, index storage [treating percentage overheads as explicit exercise assumptions rather than universal physical constants], WAL allowance, replication [such as a two-copy model representing an RDS Multi-AZ DB instance deployment: one primary plus one synchronous standby, distinct from a Multi-AZ DB cluster], retention, and backup snapshots); and cache sizing must be derived from hot-object populations, average object sizes, target hit-rates, and cache metadata overhead (treating Pareto-like 80/20 behavior as a workload hypothesis rather than an unverified assumption). Cloud cost models must parameterize Region, service tier, usage volume, unit prices, and pricing schedules rather than hardcoding sample prices as universal physical constants or production forecasts; reported estimates must specify the underlying pricing inputs. Resource pools (HTTP sockets, threads, database connections) must be isolated via the Bulkhead Pattern so that latency spikes in non-critical auxiliary services cannot saturate core application throughput. Observed simulation runs are used to inspect whether delays approximate the intended distribution and detect obvious clustering.
