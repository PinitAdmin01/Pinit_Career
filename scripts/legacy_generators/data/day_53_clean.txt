Invariant: Every object in Java has an intrinsic monitor lock. Only ONE thread can hold that monitor lock at any given time. ⚠️ Failure Mode & tryIt Bug: Failure: Synchronizing on two different lock objects (e.g. synchronized(new Object())) creates separate locks that do not protect shared state! tryIt Friction: Synchronize on a stable private final Object lock = new Object(); to enforce mutual exclusion across all threads. 💡 3-Tier Socratic Hint Ladder: [1. Nudge: "Why is "synchronized (new Object()) { count++; }" completely useless?"] → [2. Memory: "Because every thread creates its OWN new Object and locks its own private monitor! They never wait for each other."] → [3. Fix: "Synchronize on a single shared lock instance: "private final Object lock = new Object();"."] 🧩 Situational Diagnostic Puzzle: "A high-scale payments API marks its entire processPayment() method as synchronized. Latency spikes from 5ms to 8,000ms under load, and throughput collapses to 1 transaction/second. Why?" Correct: Option B) Coarse-grained locking on the entire method serialized all independent users, forcing all transactions across the entire company into a single line. • Debrief: Coarse-grained locking destroys concurrency. Synchronization must be fine-grained: lock only the specific critical section (e.g. per-account lock), not the entire business service.
