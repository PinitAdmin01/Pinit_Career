Day 39: Abstract Classes vs Interfaces & Default Method Contract Evolution Stage 2: Defensive Fluency Month 2 • Block 8 • 4 Quests 🎯 Spoken Goal & Invariant: Goal: Master the architectural distinction between abstract classes (partial state & template workflows) and interfaces (pure behavioral contracts & default methods). Invariant: A class can extend only ONE abstract superclass (sharing state/vtable), but can implement MULTIPLE interfaces (multiple typing). Interfaces decouple what code does from how it is done. ⚠️ Failure Mode & tryIt Bug: Failure: A class implementing an interface failing to declare implemented methods as "public" triggers "cannot reduce visibility". tryIt Friction: Add the public access modifier to methods implementing an interface contract and resolve diamond default method conflicts. 💡 3-Tier Socratic Hint Ladder: [1. Nudge: "All methods in an interface are implicitly public. What happens if your class implements them as package-private (without public)?"] → [2. Memory: "Java forbids reducing the visibility of an inherited method!"] → [3. Fix: "Add "public" to the method declaration in your implementing class."] 🧩 Situational Diagnostic Puzzle: "A microservice needs to audit, serialize, and process financial trades. In Java, can a Trade class extend three different classes (Auditable, Serializable, Processable)?" Correct: Option B) No, Java permits single class inheritance, but Trade can implement all three interfaces (Auditable, Serializable, Processable). • Debrief: Java prevents multiple inheritance of state (classes) to avoid the Diamond Problem, but permits multiple inheritance of type (interfaces).
