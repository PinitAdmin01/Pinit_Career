Day 37: Method Overriding, @Override, Virtual Method Tables (vtable) & Dynamic Dispatch

Stage 2: Defensive Fluency Month 2 • Block 8 • 4 Quests
🎯 Spoken Goal & Invariant:
Goal: Master method overriding, the @Override annotation, and understand runtime dynamic method dispatch via vtables.
Invariant: When invoking an overridden method on a parent reference (Account acc = new SavingsAccount()), the JVM invokes the RUNTIME subtype version.
⚠️ Failure Mode & tryIt Bug:
Failure: Misspelling an overridden method name without @Override accidentally creates a brand-new method, losing polymorphic behavior.
tryIt Friction: Add the @Override annotation to catch a signature typo (withDraw vs withdraw) at compile time.
💡 3-Tier Socratic Hint Ladder: [1. Nudge: "Why did SavingsAccount call the parent withdraw() instead of its specialized overdraft-checking logic?"] → [2. Memory: "Check spelling: the child declared "withDraw" with a capital D. It overloaded instead of overriding!"] → [3. Fix: "Add @Override above the method. The compiler will immediately flag if it does not match a parent method."]
🧩 Situational Diagnostic Puzzle: "Given: "Account acc = new SavingsAccount(); acc.applyMonthlyFee();". SavingsAccount overrides applyMonthlyFee(). The compiler looks at Account, finds the method, and compiles. At runtime, which method runs?"
Correct: Option B) SavingsAccount.applyMonthlyFee() because Java uses runtime dynamic method dispatch based on actual heap object type. • Debrief: Java uses dynamic dispatch. The compiler verifies the method exists on the reference type (Account), but the runtime executes the method from the actual object in heap (SavingsAccount).
