💡  3-Tier Socratic Hint Ladder: [1. Nudge: "Why didn't the
UserCard re-render after a background refetch confirmed identical

🧩  Situational Diagnostic Puzzle: "An engineer writes: `useQuery({
queryKey: ['user', { id, filter }], queryFn: ... })`. In another component,
they write: `useQuery({ queryKey: ['user', { filter, id }], queryFn: ... })`.
Notice the object key order is flipped. Does TanStack Query treat them
as the same query?"
Correct: Option B) Yes! TanStack Query automatically
deterministically serializes query keys, sorting object keys so that
property order does not break cache hits. • Debrief: TanStack Query
uses deterministic JSON serialization for query keys. Object keys
inside query key arrays are sorted alphabetically before hashing,
ensuring that `{ id, filter }` and `{ filter, id }` share the exact same
cache entry.

🎯  Spoken Goal & Invariant:
Goal: Master production
optimistic UI: Learn how to
deliver zero-perceived-latency
user interactions by mutating
the local cache before server
responses return, storing
previous state snapshots,
executing rollbacks on network
failure, and queueing offline
mutations.
Invariant: An optimistic
mutation requires a 3-
step contract: 1) Cancel
active queries to prevent
in-flight overwrites; 2)
Snapshot the current
cache and apply the
optimistic change; 3) If
the mutation fails,
rollback using the
snapshot; 4) On
completion, invalidate
queries to synchronize
with canonical backend
state.
⚠  Failure Mode & tryIt Bug:
Failure: Applying an optimistic
update without snapshotting
previous state: when the server
returns HTTP 500 or validation
errors, the UI remains
corrupted with false data.
tryIt Friction: Implement a
'Like' button with TanStack
Query `useMutation`: update
the count instantly, simulate a
50% network failure rate, and
verify that the count cleanly
rolls back with an error toast
on failure.
💡  3-Tier Socratic Hint Ladder: [1. Nudge: "Why must we cancel
outgoing queries with `queryClient.cancelQueries()` before applying an
optimistic update?"] → [2. Memory: "If a background refetch is already
in flight, its response could arrive 10ms later and overwrite your
optimistic update with old data!"] → [3. Fix: "Always cancel active
queries for that key before modifying the cache."]
🧩  Situational Diagnostic Puzzle: "A user on a subway train goes
through a tunnel and clicks 'Archive' on 3 emails in rapid succession. The
app is offline. How must an enterprise optimistic architecture handle
this?"
Correct: Option B) Apply all 3 archive actions optimistically to local UI
immediately, append the mutation requests to a persistent IndexedDB
queue, and drain the queue automatically when the browser fires the
`online` event. • Debrief: Production offline architecture applies
mutations optimistically to the local cache immediately, while
persisting the pending mutations in an offline queue (e.g. IndexedDB).
When connectivity returns, the queue is replayed sequentially.
