Master connection lifecycle management, heartbeat ping/pongs, and backpressure handling so a slow client does not exhaust server memory buffers!<br>

          <strong>🎯 Spoken Goal &amp; Invariant:</strong><br>
          <span style="color: #0284c7; font-weight: 600;">Goal:</span> Authentication in distributed microservices cannot rely on centralized server sessions; querying a database session on every single microsecond API call creates an intolerable bottleneck. Instead, enterprise architectures use OAuth2 Password Bearer flow with JSON Web Tokens (JWT). A JWT consists of three base64url-encoded parts: Header (algorithm and key ID), Payload (claims: sub, exp, iat, roles), and Signature (HMAC-SHA256 or asymmetric Ed25519/RS256). Because the signature is cryptographically verified using a secret key or public key, any microservice can verify the user's identity statelessly without querying a central database! But stateless JWTs have a fatal flaw: Token Revocation! If a user's token is stolen, how do you revoke it before it expires? Master Refresh Token Rotation, short-lived access tokens (15 minutes), and distributed Redis token blocklists!<br>
          <span style="color: #0369a1; font-weight: 600;">Invariant:</span> <code>JWT Security Invariant: Stateless JWT verification guarantees payload integrity via cryptographic signatures without database lookups; token revocation requires pairing short-lived access tokens (5-15 min) with stateful refresh token rotation.</code>
        </div>
        <div style="background: #fffbeb; padding: 4pt 6pt; border-radius: 3px; border: 1px solid #fef3c7; color: #92400e;">
          <strong>⚠️ Failure Mode &amp; tryIt Bug:</strong><br>
          <strong>Failure:</strong> Issuing stateless JWT access tokens with 30-day expiration dates without a revocation mechanism; an employee is fired, but their stolen JWT continues to grant full admin access to production APIs for an entire month.<br>
          <strong>tryIt Friction:</strong> Implement an OAuth2 JWT Authentication & Rotation Engine in TypeScript: generate signed JWTs with expiration claims; implement cryptographic signature verification; implement short-lived access tokens (15m) paired with rotating refresh tokens; maintain a Redis-style bloom filter blocklist for instantaneous revocation.
        </div>

        <strong style="color: #0f172a;">🧩 Situational Diagnostic Puzzle:</strong>
        <em>"A financial API uses asymmetric RS256 JWT tokens. A penetration tester modifies the JWT header from '"alg": "RS256"' to '"alg": "HS256"' and signs the token using the server's public RSA key (which is publicly accessible at /.well-known/jwks.json). The API's verification function accepts the forged token and grants the tester admin access! What is this vulnerability?"</em><br>
        <strong>Correct:</strong> Option B) Algorithm Confusion Attack (CVE-2015-9235): The verification library blindly trusts the 'alg' header in the token. When changed to HS256 (symmetric HMAC), the library uses the provided RSA public key as the HMAC symmetric secret key! Because the attacker knows the public key, they can forge valid signatures. The server must strictly enforce expected algorithms ('algorithms=["RS256"]'). &bull;
        <span style="color: #0369a1;"><strong>Debrief:</strong> Option B is correct. In an Algorithm Confusion attack, an attacker exploits libraries that dynamically pick the verification algorithm based on the token's unverified header. By switching RS256 to HS256, the server treats its own public key as a symmetric HMAC secret, allowing anyone who knows the public key to generate valid tokens. Secure implementations strictly whitelist allowed algorithms.</span>
