Master raw JDBC, PreparedStatement injection prevention, HikariCP connection pooling, and programmatic transaction management. Invariant: Opening a raw database TCP connection per request destroys latency. Connection pools maintain warm pre-authenticated sockets. Transactions require setAutoCommit(false) and explicit commit/rollback. ⚠️ Failure Mode & tryIt Bug: Failure: Concatenating user input into raw SQL strings triggers SQL injection vulnerabilities; forgetting to close a connection leaks pool sockets, deadlocking all subsequent queries. tryIt Friction: Refactor a vulnerable raw Statement into a PreparedStatement with try-with-resources and programmatic transaction commit/rollback. 💡 3-Tier Socratic Hint Ladder: [1. Nudge: "Why is "SELECT * FROM users WHERE id = " + userId an extreme security violation?"] → [2. Memory: "An attacker can pass "1 OR 1=1" and dump the entire database! Always use PreparedStatement with "?" placeholders."] → [3. Fix: "Wrap Connection, PreparedStatement, and ResultSet in try-with-resources to ensure sockets return to the HikariCP pool."] 🧩 Situational Diagnostic Puzzle: "A banking service transfers $500: it deducts from Account A, encounters an error writing the credit to Account B, and throws an exception. Account A is debited, but Account B never receives funds. Why?" Correct: Option B) AutoCommit was enabled (default true), so the debit committed immediately without an enclosing atomic transaction rollback. • Debrief: By default, JDBC auto-commits every single statement immediately. Multi-statement financial transfers MUST call connection.setAutoCommit(false), execute both updates, and call connection.commit() (or rollback() in catch).
