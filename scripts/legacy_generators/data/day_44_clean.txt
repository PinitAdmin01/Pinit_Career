Day 44: JVM Garbage Collection Anatomy & Diagnosing Real Memory Leaks
Stage 3: Systems Stress-Testing Month 2 • Block 9 • 4 Quests 🎯 Spoken Goal & Invariant: Goal: Master JVM Garbage Collection: the generational hypothesis (Eden, Survivor S0/S1, Old Gen), GC Roots, stop-the-world pauses, and how Java leaks memory via unclosed roots. Invariant: Objects are eligible for GC when they are unreachable from any GC Root (thread stack frames, static variables, active JNI handles). Static collections never die and cause real memory leaks. ⚠️ Failure Mode & tryIt Bug: Failure: Appending objects into a static collection (e.g. static List ) without removal prevents GC collection and triggers java.lang.OutOfMemoryError: Java heap space. tryIt Friction: Identify and fix a memory leak where an unclosed listener or static cache continually retains uncollectible heap objects. 💡 3-Tier Socratic Hint Ladder: [1. Nudge: "If Java has automatic garbage collection, how did the application run out of memory (java.lang.OutOfMemoryError)?"] → [2. Memory: "Because the GC only reclaims UNREACHABLE objects! If a static List holds a pointer to an object, that object is permanently reachable."] → [3. Fix: "Clear the static reference or use a bounded cache with eviction (e.g. WeakHashMap or LRU) to let the GC reclaim memory."] 🧩 Situational Diagnostic Puzzle: "A production financial microservice experiences 4-second latency freezes every 10 minutes. A heap dump reveals 95% of the heap is full of old-generation session objects. What is occurring?" Correct: Option B) A Full GC (Stop-The-World pause) is struggling to collect lingering reachable objects in the Tenured Old Gen, freezing all application worker threads. • Debrief: Full GC pauses freeze all application threads while traversing the old-generation object graph. Memory leaks that promote dead objects to old generation cause catastrophic latency spikes.
