Concept Invariant &amp; Guardrail On Android, the ART runtime enforces strict per-app heap sizes (often 256MB-512MB). Bitmaps live in native memory (Android 8+), while JavaScript lives in the Hermes heap. Memory leaks occur on both layers. Failure Mode: Holding a reference to an Android Activity context inside a static utility class causes the entire Activity and all its views to leak upon screen destruction. TryIt Friction Challenge: Capture an Android Studio memory heap dump, find a leaked Activity context reference using class path references, and sever the leak. 3-Tier Socratic Hint Ladder: 1. Nudge: Why is passing an Activity context into a long-lived singleton service a severe memory leak on Android? 2. Visual Memory: When the user presses Back, the Activity is destroyed, but the singleton keeps a pointer to it, preventing the garbage collector from freeing the Activity and its entire View tree! 3. Surgical Line Fix: Pass applicationContext instead of Activity context to long-lived singleton services. Situational Production Puzzle (FAANG / Staff Screen): Scenario: An Android banking app throws java.lang.OutOfMemoryError: Failed to allocate a byte allocation with 16777216 free bytes. LeakCanary flags an Activity leak. How is this resolved? Correct Answer: Option 2 &mdash; Inspect the LeakCanary trace: find the static reference holding the destroyed Activity context and nullify the reference in onDestroy. Debrief: LeakCanary automatically detects when a destroyed Activity remains reachable from GC roots. Severing the static reference allows the Android garbage collector to reclaim the Activity's memory.
