Invariant: Calling thread.start() spawns a new OS kernel thread. Calling thread.run() merely executes the method synchronously on the current thread! ⚠️ Failure Mode & tryIt Bug: Failure: Accidentally calling t.run() instead of t.start() runs code on the main thread, blocking the UI and failing to achieve parallel execution. tryIt Friction: Replace t.run() with t.start() to launch execution on a separate concurrent thread. 💡 3-Tier Socratic Hint Ladder: [1. Nudge: "Why is the application freezing on the main thread even though you created new Thread(runnable)?"] → [2. Memory: "Look at how you invoked it: did you call .run() or .start()?"] → [3. Fix: "Calling .run() is just a normal method call! You must call .start() to instruct the OS to spawn a thread."] 🧩 Situational Diagnostic Puzzle: "A developer creates 4 background worker threads to download files concurrently: "for (Thread t : workers) t.run();". The files download strictly one after another sequentially. Why?" Correct: Option B) Calling .run() directly executes synchronously on the calling thread. They must call .start() to initiate concurrent execution. • Debrief: t.start() allocates a new native thread and OS stack frame, then invokes run(). Calling t.run() directly bypasses thread creation entirely.
