Invariant: volatile guarantees VISIBILITY, not atomicity. Writes to volatile variables flush immediately to main memory and bypass CPU L1 caches. ⚠️ Failure Mode & tryIt Bug: Failure: A worker thread checking "while (!stopRequested)" loops forever because the write on the main thread remains in a CPU write buffer! tryIt Friction: Mark the shutdown flag "private volatile boolean stopRequested = false;" to establish a Happens-Before visibility barrier. 💡 3-Tier Socratic Hint Ladder: [1. Nudge: "Why does worker thread never see "stopRequested = true" set by main thread on a multi-core machine?"] → [2. Memory: "Because the worker thread cached the value false in its L1 CPU cache and never re-read main RAM!"] → [3. Fix: "Add "volatile" to the boolean flag: "private volatile boolean stopRequested = false;"."] 🧩 Situational Diagnostic Puzzle: "A developer writes a thread-safe counter using: "private volatile int count = 0; public void increment() { count++; }". Under 10 threads, count still produces lost updates. Why did volatile fail to make it thread-safe?" Correct: Option B) volatile guarantees visibility of reads and writes, but does NOT make compound operations (read-modify-write like count++) atomic. • Debrief: volatile ensures that every thread reads the latest value, but does not provide mutual exclusion. count++ is still three separate operations that can interleave across threads.
