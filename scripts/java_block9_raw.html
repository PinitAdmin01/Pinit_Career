Day 41 JVM Throwable Hierarchy: Throwable, Error, Exception & RuntimeException Stage 3: Systems Stress-Testing Month 2 • Block 9 • 4 Quests
🎯 Spoken Goal & Invariant:
Goal: Master the exception tree: Error (JVM fatal), Exception (Checked - must handle), RuntimeException (Unchecked - programming bugs).
Invariant: Checked exceptions force compile-time handling (try-catch or throws). Unchecked exceptions represent recoverable runtime bugs.
⚠️ Failure Mode & tryIt Bug:
Failure: Catching java.lang.Error (like OutOfMemoryError) prevents the JVM from shutting down cleanly when resources are exhausted.
tryIt Friction: Refactor "catch (Throwable t)" to "catch (Exception e)" so fatal JVM errors are not silently swallowed.
💡 3-Tier Socratic Hint Ladder: [1. Nudge: "Why is catching Throwable or Error considered dangerous in production?"] → [2. Memory: "If the JVM runs out of memory (OutOfMemoryError) or suffers StackOverflowError, catching it leaves the system in a corrupted zombie state."] → [3. Fix: "Catch specific business exceptions or at most Exception, never Throwable or Error."]
🧩 Situational Diagnostic Puzzle: "A junior developer wraps an entire microservice main loop in: "try { ... } catch (Throwable t) { log.error("Error"); }". During an OOM event, the service stays alive but drops all requests. Why?"
Correct: Option B) Catching Throwable caught OutOfMemoryError, preventing the JVM from crashing and restarting, leaving it in a degraded zombie state. • Debrief: Never catch Throwable or Error. Errors indicate unrecoverable JVM conditions. Swallowing them prevents orchestrators (Kubernetes/Docker) from detecting crashes and restarting the pod.

Day 42 Defensive Error Recovery: try-catch-finally Blocks & Exception Propagation Stage 3: Systems Stress-Testing
Month 2 • Block 9 • 4 Quests
🎯 Spoken Goal & Invariant:
Goal: Master try-catch-finally execution: stack unwinding, multi-catch blocks, and the guarantee that finally ALWAYS runs.
Invariant: The finally block executes whether an exception was thrown, caught, or not thrown — even if a return statement was executed!
⚠️ Failure Mode & tryIt Bug:
Failure: Putting a return statement inside a finally block silently discards exceptions thrown in the try block, masking critical bugs.
tryIt Friction: Remove return statements from inside finally blocks so active exceptions propagate properly.
💡 3-Tier Socratic Hint Ladder: [1. Nudge: "What happens if the try block throws an exception, but the finally block executes "return 0;"?"] → [2. Memory: "The return in finally completely swallows and discards the exception, pretending everything succeeded!"] → [3. Fix: "Never put a return statement inside a finally block."]
🧩 Situational Diagnostic Puzzle: "A transaction method throws InsufficientFundsException in the try block. The finally block contains "return true;". What does the caller receive?"
Correct: Option B) true! The return statement in finally suppresses the pending exception and returns true to the caller. • Debrief: A return in a finally block aborts any in-flight exception and forces an immediate normal return, creating a catastrophic silent failure.

Day 44 JVM Garbage Collection Anatomy & Diagnosing Real Memory Leaks Stage 3: Systems Stress-Testing
Month 2 • Block 9 • 4 Quests
🎯 Spoken Goal & Invariant:
Goal: Master JVM Garbage Collection: the generational hypothesis (Eden, Survivor S0/S1, Old Gen), GC Roots, stop-the-world pauses, and how Java leaks memory via unclosed roots.
Invariant: Objects are eligible for GC when they are unreachable from any GC Root (thread stack frames, static variables, active JNI handles). Static collections never die and cause real memory leaks.
⚠️ Failure Mode & tryIt Bug:
Failure: Appending objects into a static collection (e.g. static List) without removal prevents GC collection and triggers java.lang.OutOfMemoryError: Java heap space.
tryIt Friction: Identify and fix a memory leak where an unclosed listener or static cache continually retains uncollectible heap objects.
💡 3-Tier Socratic Hint Ladder: [1. Nudge: "If Java has automatic garbage collection, how did the application run out of memory (java.lang.OutOfMemoryError)?"] → [2. Memory: "Because the GC only reclaims UNREACHABLE objects! If a static List holds a pointer to an object, that object is permanently reachable."] → [3. Fix: "Clear the static reference or use a bounded cache with eviction (e.g. WeakHashMap or LRU) to let the GC reclaim memory."]
🧩 Situational Diagnostic Puzzle: "A production financial microservice experiences 4-second latency freezes every 10 minutes. A heap dump reveals 95% of the heap is full of old-generation session objects. What is occurring?"
Correct: Option B) A Full GC (Stop-The-World pause) is struggling to collect lingering reachable objects in the Tenured Old Gen, freezing all application worker threads. • Debrief: Full GC pauses freeze all application threads while traversing the old-generation object graph. Memory leaks that promote dead objects to old generation cause catastrophic latency spikes.
