          <strong>🎯 Spoken Goal &amp; Invariant:</strong><br>
          <span style="color: #0284c7; font-weight: 600;">Goal:</span> For decades, Python database access was synchronous and blocking. If a query took 200ms, the worker thread was frozen. In SQLAlchemy 2.0, the entire ORM was fundamentally re-architected for native asynchronous execution. An async engine (create_async_engine) wraps asynchronous database drivers like asyncpg (for PostgreSQL) or asyncmy (for MySQL). At the core of database performance is Connection Pooling. Opening a new TCP connection to PostgreSQL, performing SSL handshakes, and authenticating takes 30ms to 50ms! SQLAlchemy's QueuePool maintains a pool of pre-opened, authenticated connections (pool_size, max_overflow, pool_timeout, pool_recycle). Understand connection checkout and checkin dynamics, connection statement caching, and why improperly sized connection pools cause catastrophic connection pool exhaustion!<br>
          <span style="color: #0369a1; font-weight: 600;">Invariant:</span> <code>Connection Pool Invariant: An asynchronous database engine multiplexes queries across a bounded pool of pre-authenticated connections (QueuePool); connections must be returned immediately to prevent pool exhaustion under concurrent load.</code>
        </div>
        <div style="background: #fffbeb; padding: 4pt 6pt; border-radius: 3px; border: 1px solid #fef3c7; color: #92400e;">
          <strong>⚠️ Failure Mode &amp; tryIt Bug:</strong><br>
          <strong>Failure:</strong> Holding a database connection open while performing a slow external HTTP API call; 50 concurrent requests exhaust the connection pool (pool_size=20, max_overflow=30), causing all subsequent database queries across the entire application to hang and fail with TimeoutError.<br>
          <strong>tryIt Friction:</strong> Implement an Asynchronous Database Connection Pool in TypeScript: construct a QueuePool with poolSize=10, maxOverflow=5, and timeoutMs=500; implement async checkout() and checkin() methods; simulate 50 concurrent requests competing for connections; verify FIFO queuing, overflow scaling, and timeout rejections.
        </div>

Database CPU utilization on PostgreSQL is only 12%. Why is the API crashing if the database server is barely working?"</em><br>
        <strong>Correct:</strong> Option B) Connection Pool Exhaustion via Connection Starvation: The API's connection pool size (20 + 10 = 30 connections) is drastically undersized for 1,000 concurrent requests, or route handlers are holding connections open during non-database tasks (like template rendering or external calls), causing threads to queue up and time out waiting for a connection. &bull;
        <span style="color: #0369a1;"><strong>Debrief:</strong> Option B is correct. When client concurrency exceeds available pool capacity (pool_size + max_overflow), requests must wait in a queue for connections to be checked in. If connections are held too long or the pool is undersized relative to concurrency and query duration, requests exceed pool_timeout and fail, even if the database CPU itself is idle.</span>
